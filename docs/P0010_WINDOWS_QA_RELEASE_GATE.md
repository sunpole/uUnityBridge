# P0010 — изолированная Windows QA и безопасный порядок первого Release

**Контрольная точка:** 2026-11-01. **Режим:** только GitHub и одноразовые Windows CI runners.
**Ни один тест не обращается к рабочему каталогу пользователя.**
Релиз **не опубликован**, PR #25 остаётся Draft.

## 1. Что действительно проверяется Windows CI

Исходники: `updater/AgentUpgradeTransaction.cs`,
`tests/uUnityBridge.UpgradeTests/Program.cs`,
`agent/LocalIpcSelfTests.cs`.

| Тест | Ожидаемый результат |
| --- | --- |
| Сеть недоступна → кандидат не скачан | Отказ до остановки старого агента |
| Загрузка оборвалась → неполный файл | Несовпадение SHA-256, отказ до остановки |
| SHA-256 отличается | Отказ до замены |
| Остался неизвестный файл `.uub-next` | Блокировка без перезаписи чужого staging |
| Текущий файл эксклюзивно занят до создания backup | Отказ; прежние байты сохранены |
| Файл заблокирован после успешного backup, перед заменой | Отказ; backup сохранён, временный файл убран |
| Остановку процесса не удалось подтвердить | Отказ без замены версии |
| Новый процесс не прошёл проверку IPC `health` | Возврат точного SHA-256 прежней версии и запрос перезапуска |
| Проверка IPC выбросила исключение | Восстановление предыдущей версии |
| Новый процесс ответил успешно | Новая версия активна, резервная копия сохранена |
| Настоящий канал Windows Named Pipe `CurrentUserOnly` | Сообщения `health`/`capabilities` принимаются, неизвестная команда отклоняется |
| Попытка вызвать helper без локального разрешения | Блокировка; файл назначения не создаётся |

**Тесты обновления — fault injection.** «Сбой сети» смоделирован
отсутствующим/неполным скачанным файлом: это проверяет безопасный
отказ на файловом этапе, но НЕ является тестом действительного разрыва
сетевого соединения `gh release download`.
«Занятый EXE» смоделирован Windows `FileStream` с эксклюзивной блокировкой,
а не реальным приложением в чужой пользовательской сессии.
Фальшивые EXE в файловой матрице содержат только тестовый текст;
ни один не запускается. Для IPC используется настоящая локальная
Named Pipe в рамках тестового процесса, а не постоянно установленный сервис.

Тесты используют изолированный `RUNNER_TEMP` с проверкой
`GITHUB_ACTIONS=true`. Они не могут читать или изменять пользовательские
`C:\!CODE_CLUB`, `%LOCALAPPDATA%`, настройки автозапуска либо процессы на
ПК пользователя. Подтверждение `CI PASS` не равно `E2E PASS`.

## 2. Технические ворота перед публикацией

1. Провести ревью и получить PASS всех Windows workflows для **точного HEAD**
   текущего PR, включая проверку манифеста, безопасности ZIP,
   `AgentUpgradeTransaction` и `LocalIpcSelfTests`.
2. В **отдельной Windows VM/одноразовом тестовом профиле обычного пользователя**
   проверить настоящую программу 0.4.2 с обновлятором 0.4.0:
   неработающий агент, работающий агент, отказ доступа, занятый EXE,
   сбой запуска новой версии и возврат старой с тем же SHA-256.
   GUI должен показать безопасный результат. Не проводить этот тест на
   рабочем `uUnityBridge_App`.
3. Проверить цепочку обновления Desktop 0.4.2 → 0.4.3 через **старый**
   установленный Updater 0.4.0, без перезаписи занятого exe. Важно: прежний
   Updater обновляет только Desktop; новый helper для Agent скачивает
   Desktop 0.4.3 из следующего Release. Не считать Updater 0.4.0
   автоматически заменённым на 0.4.3.
4. На VM проверить явное GUI-согласие «Обновить агент», выбор
   единственного прежнего Agent 0.2.1, SHA-256 обоих скачанных файлов
   (Agent и новый helper), контроль версии, перезапуск/rollback,
   сохранение автозапуска и локальных данных. Никакого `install_release`
   из GitHub, пока это не завершено.
5. На VM создать **отдельную пустую** папку, локально разрешить профиль
   «Папка сборок», затем проверить одно реальное `install_release`
   с правильными ID Release, asset и успешного `main` CI,
   повтор задания и неверную контрольную сумму.
   Ответ PASS означает **установку файлов**, а не работоспособность GUI.
6. До стабильного распространения защитить `main`, Release
   workflow и права публикации, рассмотреть цифровую подпись/аттестацию.
   SHA-256 и успешный CI сами по себе не гарантируют происхождение издателя.

## 3. Порядок безопасной публикации

1. **До всех локальных приёмочных тестов:** сохранить draft PR #25,
   не публиковать v0.4.3, не отправлять `install_release` на ПК.
   Для изолированных QA использовать CI artifacts/VM и их локальные копии,
   не заменяя установленный пользователем Desktop и Agent.
2. После PASS Windows VM acceptance и код-ревью: проверить базовую ветку
   `main`, объединить **существующий** PR #25; повторить CI на `main`.
3. Проверить, что `src/uUnityBridge.csproj` соответствует `0.4.3`,
   Release assets включают `uUnityBridge.exe`, updater, ZIP и
   `uUnityBridge.Agent.exe` с опубликованными SHA-256 digest.
   Запустить existing `release-windows.yml` на `main` с
   `version=0.4.3`, без перезаписи предыдущего Release.
   Workflow дополнительно обязан выполнить UpgradeTests и IPC-self-test.
4. После публикации проверить окончательный tag→SHA→run→asset ID→digest,
   реальные размеры и версии. При несоответствии — остановить rollout,
   не использовать неподтверждённые файлы.
5. Пользователь **один раз** открывает прежний Desktop 0.4.2:
   существующий автоапдейтер обновляет **только Desktop** до 0.4.3,
   после проверки которого пользователь нажимает в GUI «Обновить агент»
   и подтверждает локальный путь. Новый helper обновляет Agent 0.2.1
   до проверенной версии с backup и IPC health.
6. Только после подтверждения новой версии Agent, разрешения отдельной
   тестовой папки через GUI и нового `status` PASS из GitHub
   разрешено тестовое `install_release`. Затем — проверка
   повторов, состояния, ошибок и восстановление.
7. До появления P0014/P0015 **не обещать** запуск приложений,
   скриншот окна или визуальную приёмку. Код доставки не является
   удалённым терминалом, а ChatGPT не работает бесконечно в фоне.

## 4. Что остаётся за границами этой QA

- Никакой реальной симуляции сетевого outage GitHub/CDN с восстановлением загрузки.
- Никакой гарантии PowerShell/Windows GUI не требующей ручного согласия
  при первом bootstrap.
- Никакого доказательства user-session IPC при обычном пользователе
  после полной перезагрузки; нужен VM и затем отдельная проверка с разрешения владельца.
- Нет кодовой подписи Authenticode/attestation и установленной защиты `main`.
- Нет реального полного E2E с опубликованным `install_release` из GitHub.
- Нет изменений файлов на рабочем компьютере пользователя.
