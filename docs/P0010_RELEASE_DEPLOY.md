# P0010 — GitHub Release → Windows Agent → разрешённая папка

**Статус: код на проверке в PR; установка на компьютере пользователя не подтверждена.**
Скриншотер, удалённый запуск EXE, произвольный shell и самостоятельное обновление агента
**в этот этап не входят**.

## Цикл без PowerShell у пользователя

1. GitHub Actions собирает и проверяет проект в Windows CI.
2. Из проверенного коммита \`main\` публикуется стабильный GitHub Release с ZIP-архивом.
3. Пользователь ОДИН РАЗ в окне uUnityBridge нажимает «Папка сборок»,
   выбирает выделенный пустой каталог и явно разрешает профиль.
   Разрешение хранится только в \`%LOCALAPPDATA%\uUnityBridge\deployment-profiles.json\`.
4. ChatGPT через GitHub создаёт Issue строго определённого типа
   \`install_release\` без локальных путей и команд.
5. Работающий агент версии **0.3.0-preview или новее** проверяет автора,
   локальный профиль, номер релиза, ID asset, точный SHA-256,
   успешный CI run для commit SHA тега и ZIP.
6. Агент устанавливает распакованные файлы в
   \`<разрешённая папка>\current\`, предварительно сохранив старую версию
   в \`backups\`. При ошибке замены восстанавливает предыдущую папку.
7. Агент отвечает в Issue \`PASS\`, \`BLOCKED\` либо \`FAIL\`,
   добавляет маркер идемпотентности и закрывает Issue.

В публичном отчёте нет локального пути или токенов. Отсутствие локального
разрешения = \`BLOCKED: local_approval_missing\`, никаких загрузок или установок.

**Важно:** старый агент 0.2.1 не умеет читать \`install_release\`.
Предусмотрен GUI-bootstrap после публикации проверенного stable Release; пока это код в draft PR, а не выполненная установка.
Нельзя запускать произвольную сборку или считать новую функцию установленной
на Windows только из-за зелёного CI.

## Однократное обновление агента без ручного скачивания (новый код PR #25)

В тот же PR добавлен GUI-сценарий **«Обновить агент»**.
Используется уже существующий канал автообновления Desktop 0.4.2:
после объединения проверенного PR и публикации стабильного Release
Desktop сам получает новую версию. Затем пользователь один раз
подтверждает агенту обновление в интерфейсе, без PowerShell или
ручного скачивания EXE/ZIP.

1. Desktop 0.4.3 предлагает обновить Agent. По умолчанию выбирает
   соседний Agent EXE; если он установлен отдельно, пользователь **локально**
   указывает существующий Agent EXE через стандартное окно выбора файла.
2. Получает метаданные только последнего стабильного Release
   `sunpole/uUnityBridge`, сверяет успешный `release-windows.yml` workflow
   для точно того же commit, обязательные SHA256 digest и размеры двух assets:
   `uUnityBridge.Agent.exe`, `uUnityBridge.Updater.exe`.
3. Скачивает оба файла в ограниченный staging в LocalAppData.
   После сравнения SHA256 пользовательское разрешение привязывается
   к конкретному пути, SHA, случайному одноразовому nonce и короткому TTL.
4. Запускается **отдельный** новый helper из проверенного Release.
   Это важно: оставшийся у Desktop 0.4.2 старый Updater не поддерживает
   функцию обновления Agent, и его НЕ пытаются заменить во время работы.
5. Helper, работающий **без администратора**, проверяет разрешение,
   целевой файл и staging, создаёт резервную копию, останавливает
   только процесс с точно совпадающим полным путём в текущей сессии,
   подменяет exe и проверяет новый ответ IPC `health`.
   При сбое пытается восстановить старую версию и запустить её.
6. Локальный результат: `%LOCALAPPDATA%\\uUnityBridge\\agent-updater-last.txt`.
   Ни одно из этих действий не запускается удалённым Issue.

Новые assets Agent публикуются в стабильный Release существующим
`.github/workflows/release-windows.yml`; в PR проверена сборка, а не
реальная установка на компьютере пользователя. Старый стабильный
Release `v0.4.2` **не содержит** этих файлов.

**Ограничения:** первоначальное обновление требует согласия пользователя
в GUI; сценарий отказа в правах, неподписанные бинарники и проверка
реальной перезагрузки Windows требуют локального QA. Не обещать
бесшовность до такого теста. Защита релиза зависит от управления
репозиторием и GitHub Actions; SHA не заменяет цифровую подпись.

## Доверие и разрешения

Локальный профиль содержит:

- \`id\` — короткий идентификатор, например \`uunity\`;
- \`repository\` — фиксированный репозиторий \`sunpole/...\`;
- \`assetName\` — конкретное имя ZIP, без шаблонов;
- \`entrypoint\` — основной EXE, ожидаемый в корне архива;
- \`workflowFile\` — конкретный GitHub Actions workflow;
- \`installRoot\` — только локальный абсолютный путь, выбранный через GUI;
- \`enabled\` — явное разрешение, которое можно отозвать в GUI.

Действие из Issue не может создавать или редактировать этот профиль.
Первое развёртывание запрещено, если каталог \`current\` уже существует без
признаков управляемой установки. Повторная версия или откат к старому релизу
блокируется. Повторная обработка того же задания не переустанавливает файлы.

## Формат Issue

Заголовок:

\`\`\`text
[UUB JOB R000101]
\`\`\`

JSON-тело (значения идентификаторов и SHA-256 — **примерные**, не готовое
задание для выполнения):

\`\`\`json
{
  "schema": "uub.agent.job.v1",
  "id": "R000101",
  "action": "install_release",
  "profile": "uunity",
  "tag": "v1.2.3",
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "releaseId": 123,
  "assetId": 456,
  "runId": 789
}
\`\`\`

Номера и хеш следует получать непосредственно из проверенного GitHub Release,
а не придумывать. Парсер требует ровно девять полей, отклоняет лишние ключи,
произвольные URL, пути, команды и чужих авторов.

## Что делает агент с ZIP

- Проверяет ID/тег стабильного релиза, asset ID и имя/размер ZIP.
- Если GitHub API предоставляет \`asset.digest\`, дополнительно сверяет его.
- Проверяет успешный \`main\` CI run и совпадение его \`head_sha\` с коммитом тега.
- Пересчитывает SHA-256 скачанного ZIP до распаковки.
- Запрещает абсолютные пути, \`..\`, NTFS ADS, имена устройств Windows,
  обратные слеши, повторы имён без учёта регистра, symlink/special entries,
  чрезмерное число/размер файлов и подозрительное сжатие.
- Распаковывает в новую папку временного размещения, сохраняет маркер управления,
  перемещает старую версию в резерв и меняет целую папку \`current\`.
- Не запускает и не исполняет код архива и не запрашивает права администратора.
- Локальный журнал и содержимое ZIP не отправляет в публичный GitHub.

## Степень проверки и ограничения

Значение \`PASS: installed_files_verified\` означает только успешную
проверку происхождения на уровне release/CI, контрольной суммы,
распаковки и размещения файлов. **Не означает** успешный запуск,
проверку GUI, антивирусную проверку или криптографическую подпись издателя.
SHA-256 из Issue и Release сам по себе не заменяет Authenticode/attestation:
необходимо защищать \`main\`, CI workflow, права на релизы и GitHub-аккаунт.
Для production требуется независимая подпись/аттестация сборки и проверка
цепочки происхождения, прежде чем считать доставку полностью доверенной.

Прежние обновления uUnityBridge.exe и обновления отдельно работающего
агента не объединены этим PR. Обязательная следующая QA-проверка — обычная
Windows-сессия, заранее выбранная тестовая папка, release с фиктивной
тестовой программой, повтор задачи, сломанный архив, заблокированный
запущенный EXE и возврат предыдущей папки.
